# Журнал решений

## DEC-001: Vue SPA

**Статус:** принято.

Frontend создаётся как Vue 3 SPA на Vite с TypeScript, Pinia и Vue Router. SSR не требуется для MVP игры.

## DEC-002: Строгий TypeScript

**Статус:** принято.

Включён строгий TypeScript, `any` запрещён. Внешние данные рассматриваются как неизвестные до проверки на границе API.

## DEC-003: Сокращённый FSD

**Статус:** принято.

Используются `app`, `pages`, `features`, `shared`. Слои `entities` и `widgets` добавляются по фактической потребности, чтобы не создавать пустую архитектуру.

## DEC-004: Pinia Setup Stores

**Статус:** принято.

Все Pinia stores создаются функцией setup. Локальное UI-состояние не переносится в store без необходимости.

## DEC-005: Shared transport, feature API

**Статус:** принято.

Общий HTTP-клиент и инфраструктура находятся в `shared/api`; предметные запросы принадлежат feature. Компоненты не вызывают raw `fetch`.

## DEC-006: MSW вместо прямого mock-импорта

**Статус:** заменено решением DEC-021.

MSW перехватывал сетевой контракт в браузере и Vitest. Подход заменён прямым TMDB-адаптером frontend-прототипа.

## DEC-007: Afpia code style

**Статус:** принято.

Проект использует `@afpia/eslint`, `@afpia/prettier` и ESLint 9. `oxlint` и `oxfmt` удаляются, чтобы избежать конкурирующих правил.

## DEC-008: PrimeVue Aura

**Статус:** заменено решением DEC-014.

Для доступных базовых controls используется PrimeVue с Aura. Внешний вид адаптируется design tokens и обычным CSS.

## DEC-009: Ограниченное persistence

**Статус:** принято.

В localStorage сохраняются только текущая игра и тема. История и статистика откладываются до отдельного продуктового решения.

## DEC-010: Frontend-only MVP не является защищённой игрой

**Статус:** принято временно.

Mock-ответы доступны в клиентском bundle. Перед публичным запуском проверка ответа, а перед будущим многопользовательским
режимом также расчёт очков, обязательно переносятся на backend.

## DEC-011: Единое размещение инфраструктуры приложения

**Статус:** принято.

Все Pinia stores располагаются в `shared/stores`, Vue Router — в `app/router.ts`, а статические ресурсы и глобальные стили — в `shared/assets`. Папка `app/router/` создаётся только при реальной декомпозиции router на несколько файлов.

## DEC-012: Один сортировщик импортов

**Статус:** принято.

Импорты сортирует только `@afpia/prettier`. Сортировка импортов в ESLint отключена, чтобы автофиксы ESLint и Prettier не конкурировали.

## DEC-013: Внешние scoped-стили компонентов

**Статус:** принято.

CSS Vue-компонента хранится в соседнем файле с тем же PascalCase-именем и подключается через `<style scoped src="./ComponentName.css"></style>`. Inline CSS внутри `.vue` не используется. Глобальные tokens и базовые стили остаются в `shared/assets`.

## DEC-014: shadcn-vue вместо PrimeVue 5

**Статус:** принято.

PrimeVue 5 требует лицензионный ключ и показывает сообщение при его отсутствии. Базовые controls переносятся на
shadcn-vue с MIT-лицензией и локальным исходным кодом. Tailwind utility-классы разрешены только внутри `shared/ui`, чтобы
страницы и feature-компоненты сохраняли внешние CSS-файлы по DEC-013.

## DEC-015: TMDB как источник каталога прототипа

**Статус:** принято временно.

Браузерный адаптер получает каталог, метрики известности, названия, постеры и backdrops напрямую из TMDB. Тестовые
fixtures существуют только в тестах. `VITE_TMDB_READ_TOKEN` задаётся владельцем в `.env.local`, не коммитится и считается
публично доступным в браузере. Перед production интеграция, игровая сессия и проверка ответа переносятся на backend.

## DEC-016: Сложность вместо очков в одиночной игре

**Статус:** дополнено решениями DEC-017 и DEC-020.

Одиночная игра не начисляет очки. Пользователь выбирает один из пяти режимов, каждый из которых соответствует своему
процентилю известности внутри каталога. Очки и соревнование откладываются до многопользовательского режима. Текущий UI
не показывает управление видео или звук, потому что раунд состоит только из статических изображений.

## DEC-017: Непрерывная игровая доска

**Статус:** принято.

Отдельный стартовый экран и публичный маршрут раунда удаляются. Игра автоматически открывается на `/`; сложность можно
переключать в любой момент. Пустое действие пропускает кадр, а выбранный вариант автодополнения можно отправить как
ответ. Верный ответ повышает сложность, а победа в `impossible` сбрасывает цикл к `easy`.

## DEC-018: Жанр и перезапуск раунда в боковой панели

**Статус:** принято.

Левая панель содержит компактный выбор сложности без описаний, восемь вариантов жанра и перезапуск раунда. Жанр
фильтрует выбор фильма и сохраняется при ручном или автоматическом перезапуске. В localStorage хранится только внутренний
идентификатор активного состояния и жанр; правильный ответ и изображения не сохраняются.

## DEC-019: Процентильная известность и безопасные кадры

**Статус:** дополнено решением DEC-020.

Сложность фильма определяется его процентилем в пуле, отсортированном по составной оценке `vote_count` и `popularity`:
10% `easy`, 20% `medium`, 25% `hard`, 25% `expert`, 20% `impossible`. Пять backdrop-изображений автоматически
упорядочиваются по эвристике узнаваемости. Tesseract.js исключает кадры, в которых OCR находит русское, английское,
оригинальное или альтернативное название фильма. Семантические категории кадров считаются приближением до появления
редакторской разметки или vision-модели.

## DEC-020: Полный доступный каталог вместо фиксированного пула

**Статус:** принято.

Moviestr не ограничивает игру первыми 250 фильмами. Для каждого жанра используется весь диапазон результатов,
доступный через пагинацию TMDB Discover. Чтобы frontend-прототип не загружал сотни страниц на каждый раунд, приложение
получает размер каталога, выбирает случайную позицию внутри процентиля сложности и загружает только соответствующую
страницу. Discover сортируется по `vote_count.desc`, а фильмы выбранной страницы дополнительно ранжируются по составной
оценке `vote_count` и `popularity`. Ограничение числа страниц со стороны TMDB остаётся внешним ограничением провайдера.

## DEC-021: Прямой TMDB-адаптер и объединённая загрузка фильма

**Статус:** принято для frontend-прототипа.

Runtime MSW и искусственная задержка удаляются. Создание раунда выполняется прямым TMDB-адаптером, а состояние активного
раунда хранится локальным session-адаптером. Данные фильма, альтернативные названия и изображения запрашиваются одним
TMDB movie details запросом через `append_to_response`; одинаковые запросы дедуплицируются и кэшируются в памяти.

Ошибка OCR не должна отбрасывать все изображения кандидата: после ошибки или исчерпания короткого бюджета используются
кадры без языковой маркировки TMDB. Первый кадр загружается в размере `w780`, а остальные кадры текущего раунда
предзагружаются в фоне. Тестовые fixtures не входят в runtime-код.

## Как добавлять решение

Новое архитектурное решение добавляется отдельным разделом `DEC-NNN` со статусом, контекстом, решением и последствиями. Старое решение не удаляется: оно помечается заменённым и ссылается на новое.
