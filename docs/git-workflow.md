# Git workflow

`main` и `dev` — постоянные защищённые ветки. Разработка начинается от актуальной `dev` в `feature/<name>` или
`fix/<name>`. Новые сценарии и крупные изменения сначала описываются SDD; небольшой технический fix не требует новой спеки.
Не обходить Validate/Build и не переписывать историю. Решение о merge принимает владелец.

## Завершение задачи

1. Проверить реализацию, создать атомарные коммиты и PR рабочей ветки в `dev`.
2. После принятия PR слить в `dev` и дождаться успешных проверок exact merge commit.
3. Создать **annotated** временный тег на этом merge commit: `dev/<feature>-<uniquePRorDate>`, например
   `dev/rooms-pr-42` или `dev/rooms-20261028-153000`. Проверить отсутствие такого тега локально и на remote;
   существующие теги не перемещать и не перезаписывать.
4. Опубликовать только этот тег, не использовать массовые `--tags` / `--follow-tags`.
5. Только после успешной публикации тега удалить слитую рабочую ветку локально и на remote. Проверить, что её tip
   достижим из `dev`. `main` и `dev` не удалять. Тег хранит ориентир завершённой задачи.

Нельзя удалять ветку до merge или при неуспешной публикации тега. Создание тега — не автоматический production deploy.
Принятый владельцем merge разрешает весь описанный хвост: тегирование, публикацию конкретного тега и удаление
слитой рабочей ветки при успешных проверках. Повторного подтверждения на каждый шаг не требуется.

## Релиз

1. Выполнить обычный merge `dev` → `main` через PR. **Не squash и не rebase**: ancestry промежуточных dev commits сохраняется.
2. Дождаться Validate/Build на exact release commit в `main`.
3. Создать annotated `v<SemVer>`, например `v1.2.0`, на этом exact commit и успешно опубликовать только этот тег.
4. Дождаться успешного завершения обязательных release checks и всего процесса публикации версии. Один push тега
   или старт pipeline недостаточен. Затем получить неизменяемый target через `git rev-parse v1.2.0^{commit}`. Найти только теги `dev/*`,
   чьи разыменованные commits являются ancestors этого target (`git merge-base --is-ancestor`). Сопоставить remote
   refs с локальными и только затем удалить выбранные локальные и remote dev-теги.
5. Не использовать подвижный `main`/`dev` как замену target version commit. Не удалять dev-теги вне этого ancestry,
   любые `v*` теги, постоянные ветки или несвязанные refs. При расхождении remote target остановить очистку.

Если проверки, публикация или сверка refs не прошли, очистка не выполняется. Частичный сбой удаления надо явно
сообщить; нельзя расширять набор удаления. Удаление тегов и веток выполняется только в рамках разрешённого этапа.
Принятый владельцем release разрешает предусмотренное тегирование и очистку вошедших dev-тегов после успешной
публикации версии; отдельное повторное разрешение на эти шаги не требуется.

## CI

PR и push в `main`/`dev` запускают Validate и Build. Push `dev/*` — проверка промежуточного dev tag;
push `v*` — проверка SemVer release tag. Context job различает эти каналы; ни один job не создаёт/не публикует
теги, не удаляет refs, не сливает PR и не запускает production deploy. CI token остаётся read-only.

В задаче настройки workflow существующие ветки, теги, PR и релизы не изменяются. Сам текст этих правил не является
разрешением немедленно выполнять операции на remote.
