# Функциональные спецификации

Спецификация описывает наблюдаемое поведение продукта независимо от конкретной реализации. Инженерные детали приводятся
только тогда, когда являются частью контракта, ограничения безопасности или измеримого нефункционального требования.

## Состав документа

Каждая спецификация содержит:

1. метаданные и статус;
2. цель и пользовательскую ценность;
3. границы и явно исключённые сценарии;
4. требования со стабильными ID;
5. состояния и переходы;
6. сценарии приёмки в формате Given/When/Then;
7. ошибки и пограничные случаи;
8. трассировку на код и тесты;
9. открытые вопросы и ограничения.

Новый документ создаётся по [`_template.md`](./_template.md). ID спецификации не переиспользуется после удаления или
замены. ID требования сохраняется при редакционном уточнении и меняется только при появлении нового самостоятельного
поведения.

## Реестр

| ID       | Область                 | Требования | Статус      |
| -------- | ----------------------- | ---------- | ----------- |
| SPEC-001 | одиночный игровой цикл  | `SOL-*`    | реализовано |
| SPEC-002 | каталог и выбор кадров  | `CAT-*`    | реализовано |
| SPEC-003 | поиск и проверка ответа | `SRC-*`    | реализовано |
| SPEC-004 | интерфейс игровой доски | `UI-*`     | реализовано |
| SPEC-005 | persistence и тема      | `PER-*`    | реализовано |

## Правило трассировки

Таблица трассировки указывает основное место реализации и тесты, подтверждающие требование. Она не обязана перечислять
каждый вспомогательный файл. Если требование реализовано, но не имеет автоматической проверки, это явно отмечается как
технический долг, а не скрывается статусом документа.
