## Цель и границы

Вынести из frontend серверную игровую логику, локальную заглушку комнат и TMDB-интеграцию в отдельное NestJS-приложение.
Frontend остаётся Vue-клиентом: отображение, ввод, клиентский поиск с debounce, transport, UI-state и настройки интерфейса.
Backend реализован отдельно. По запросу владельца от 28 октября выполнено полное подключение frontend и удаление
заменённой серверной реализации. План frontend: [`frontend-plan.md`](./frontend-plan.md).
Локальная topology: Docker PostgreSQL + API + nginx frontend, внешний origin `http://localhost:8080`.

Без регистрации, аккаунтов, OAuth, чата, голоса, рейтинга между матчами и платных AI-сервисов.
Временная гостевая сессия нужна для проверки прав и восстановления; никнейм не является доказательством личности.

## Требования

- **BE-001.** NestJS + TypeScript обслуживает HTTP API и realtime; PostgreSQL хранит гостевые сессии, соло и комнаты.
  Точный ORM, версия PostgreSQL и хостинг выбираются при подготовке backend, а не подразумеваются согласованными.
- **BE-002.** Backend — единственный источник истины для фильма, ответа, кадров, счёта, таймера и прав хоста.
  Клиент не передаёт доверенные score, correct, deadline, hostId или свою роль.
- **BE-003.** Соло сохраняет SOL-001–SOL-014: автоматический старт, пять кадров, свободный выбор сложности/жанра,
  пропуск, сдача, победа, повтор и цикл сложности. Очков и таймера в соло нет.
- **BE-004.** Поиск работает по русским и английским названиям; результаты `MovieSuggestion` объединяются по ID,
  максимум 10. ID формата `tmdb-603` сохраняются.
- **BE-005.** Новый API проверяет выбранный `movieId` в обоих режимах. Смена title → movieId согласована этапом интеграции;
  клиент передаёт ID из поиска и expectedFrameIndex, в комнате также roundId.
  Русское/английское название одного TMDB ID означает один и тот же фильм; совпадающий title другого ID не подходит.
- **BE-006.** Сохраняются публичность, необязательный пароль, 2–4 места, старт хостом от двух игроков, 1–50 фильмов
  (по умолчанию 20), сложности и жанры из MP-001–MP-008.
- **BE-007.** В матче один фильм и последовательность пяти кадров для всех; личный текущий кадр и попытки независимы.
  Все начинают с 1000 очков; верно +100 один раз, каждый новый неверный ID −50 и следующий кадр.
  Ошибка на пятом кадре завершает фильм без второго штрафа; пропуски 1–4 бесплатны, сдача/таймаут −50 один раз.
- **BE-008.** Общий серверный таймер — 90 секунд после готовности фильма. Завершение всеми или deadline открывает общий
  reveal. Только readiness всех участвующих переводит матч дальше; после последнего reveal — в итог.
  Все N фильмов различны; финальная ничья даёт нескольких победителей. Отрицательные очки допустимы.
- **BE-009.** Переподключение восстанавливает состояние; после 30 секунд отсутствия хоста роль переходит следующему
  активному по порядку входа. Выход, закрытие комнаты и ошибки подготовки сохраняют правила MP-021–MP-025.
- **BE-010.** Ответ, названия, aliases, TMDB ID загаданного фильма и неоткрытые кадры не попадают в активный snapshot.
  Чужие ответы и личные кадры не передаются. Правильный фильм раскрывается в серверной фазе round-result, только после
  завершения всеми; рядом показывается персональный исход. До этой фазы result/roundResult отсутствуют (null).
- **BE-011.** Дубликаты, параллельные команды и устаревшие round/frame IDs не изменяют счёт и кадр повторно.
  Таймер работает без запросов браузера; после перезапуска backend восстанавливается из БД.
- **BE-012.** Каталог, ранжирование, выбор пяти кадров, OCR и TMDB token полностью находятся на backend.
  Сохраняются диапазоны 0–10 / 10–30 / 30–55 / 55–80 / 80–100%, без Top 250, внутри выбранного жанра.
- **BE-013.** Разрыв сети, ошибка TMDB/OCR/БД и неготовый API не засчитываются как неверная попытка.
  Подготовка фильма не расходует 90 секунд; повтор не меняет уже зафиксированные очки или номер фильма.
- **BE-014.** Demo runtime, sessionStorage с ответами и Vercel TMDB-функция удаляются только после подключения и
  проверки соответствующей серверной замены. Тема, жанр, ID восстановления и UI-storage не удаляются без причины.

## Принятые технические решения

HTTP-команды + native WebSocket-события, персональные snapshots, opaque HttpOnly guest cookie для HTTP,
одноразовый realtime ticket для WS, один backend instance в первой версии, без Redis и микросервисов.
Две вкладки с общей cookie представляют одного гостя; независимые игроки — разные браузерные контексты/устройства.
Эти решения подтверждены запросом на интеграцию 28 октября. Контракт 0.1.0: соседний moviestr-back/docs/api/handoff.md,
OpenAPI и websocket.schema.json. POST games возвращает 202 и operationId; frontend опрашивает персональный GET game.
Команды используют Idempotency-Key, повтор не меняет ключ. Ошибка авторизации не повторяет mutation от новой личности.

## Состояния и приёмка

Комната: `waiting -> loading -> playing -> round-result -> loading -> ... -> round-result -> finished`;
`loading -> error -> loading`; закрытие — `closed`. В `round-result` нет currentFrame/deadline, есть result и personal
roundResult. Только POST ready всех required participants переводит в следующий фильм/итог; клиент не делает автопереход.
Игрок: `playing / won / lost`, отдельно connected/left. Соло: текущие `GameResponse` и состояния store.

- **AC-01:** два отдельных устройства создают/открывают комнату; видят один фильм, личные кадры и общий рейтинг.
- **AC-02:** неверный ответ и затем верный дают 1050; второй игрок остаётся на своём кадре и не получает ответ.
- **AC-03:** двойная отправка, одновременный старт, гонка последнего места и ответ на границе deadline безопасны.
- **AC-04:** закрытие вкладки не останавливает серверный таймер; refresh/reconnect и restart backend восстанавливают матч.
- **AC-05:** соло открывается без регистрации, поиск RU/EN и восстановление работают; в браузере нет правильного ответа.
- **AC-06:** токена TMDB нет в dist/Network/storage; frontend после миграции не выполняет OCR, выбор фильма или начисление очков.

## Вопросы перед реализацией

Production hosting, публичный backend URL, TLS/domain и cutover остаются отдельным решением. Не заказывать сервисы
и не менять опубликованный Vercel deployment без отдельного запроса. Локальные контракты и Docker не требуют этого выбора.
