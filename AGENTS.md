# Правила проекта Moviestr

Файл действует на весь репозиторий. Moviestr — браузерная Vue-игра: пользователь сразу начинает одиночный раунд и
угадывает фильм по пяти кадрам. Каталог и изображения поступают из TMDB. Мультиплеер реализован как локальное демо
между вкладками одного браузера; backend комнат и авторизация отсутствуют. TMDB-токен хранится в серверной функции Vercel.

## Источники требований

Приоритет: последнее решение владельца → связанный `docs/<feature>/spec.md` → этот файл → код и тесты.
`docs/README.md` содержит индекс SDD-пакетов. Перед изменением поведения прочитать `spec.md`, `plan.md` и `tasks.md`
затрагиваемой возможности. Если код расходится со спецификацией, определить причину: дефект исправлять по требованиям,
а согласованное изменение поведения сначала отразить в требованиях.

Новая функциональность и изменение пользовательских сценариев, правил игры или контрактов требуют SDD-пакета.
Крупная задача также требует SDD и отдельной feature-ветки: например, самостоятельная архитектурная переработка,
изменение нескольких связанных slices, публичных контрактов, хранения данных или критических переходов игры.
Оценивать сложность по связанности и риску, а не только количеству файлов. Формулировка владельца «сделать фичу»
всегда запускает этот процесс, даже если реализация небольшая.
Если пакета нет, создать его по `docs/_template` на основе запроса и уже принятых решений. Задавать вопросы только о
существенных недостающих требованиях; отсутствие файлов само по себе не требует опроса или повторного согласования.

Небольшие технические исправления с известным ожидаемым результатом — CSS, опечатки, типы, настройка инструментов, рефакторинг
без изменения поведения и исправление бага — не требуют нового SDD-пакета. Прочитать связанные требования, если они
есть, исправить и проверить. Если исправление меняет продуктовые правила или перерастает в крупную архитектурную задачу,
применить SDD-процесс.

## SDD-процесс

1. **Spec** — описать цель, границы, проверяемые требования, состояния, ошибки и критерии приёмки в `spec.md`.
2. **Plan** — определить FSD slices, контракты, данные, API, этапы, риски и проверки в `plan.md`.
3. **Tasks** — разбить реализацию на атомарные проверяемые пункты в `tasks.md`.
4. **Implement** — выполнять задачи по порядку без неподтверждённых расширений.
5. **Verify** — выполнить проверки по риску изменения и сверить результат с затронутыми requirement ID.

Новый пакет создавать по `docs/_template`. До согласования он имеет статус `черновик`. Завершённую задачу отмечать
только после реализации и проверки. Исправление дефекта не требует новой спецификации, если ожидаемое поведение уже
задано. Явный запрос владельца и его ответы считаются согласованием описанных в них требований; новые спорные решения
оставлять открытыми до уточнения.

## Проектные скиллы

Инструкции находятся в `.codex/skills`. Перед соответствующим этапом прочитать нужный `SKILL.md`:

- [`sdd-feature`](.codex/skills/sdd-feature/SKILL.md) — создание или изменение функциональности: Spec → Plan → Tasks → Implement.
- [`verify-changes`](.codex/skills/verify-changes/SKILL.md) — проверка реализации, тесты, линтеры и сверка с требованиями.
- [`commit-changes`](.codex/skills/commit-changes/SKILL.md) — атомарный коммит завершённой и проверенной части работы.

Обычная последовательность: `sdd-feature` → `verify-changes` → `commit-changes`. Для технического исправления начинать
с реализации, затем проверки и коммита. Запрос только на анализ или проверку не разрешает менять код или создавать коммит.
Общие ограничения и формат Git определены здесь; скиллы описывают выполнение этапов и не расширяют запрос владельца.

## Проектные агенты

[`reviewer`](.codex/agents/reviewer.toml) — агент для ревью diff, коммита или диапазона изменений по запросу владельца.
Проверяет дефекты, регрессии, соответствие SDD и границы FSD; возвращает замечания с приоритетами и ссылками на строки.
Не изменяет файлы и не создаёт коммиты. Его ревью дополняет `verify-changes`, но не заменяет тесты и линтеры.

## Стек и архитектура

- Vue 3, TypeScript strict, Composition API, `<script setup lang="ts">`, Vite.
- Pinia Setup Stores и Vue Router.
- shadcn-vue; Tailwind CSS разрешён только внутри `shared/ui`, в приложении используется обычный scoped CSS.
- Vitest, Vue Test Utils и jsdom.
- Yarn 1, `@afpia/eslint`, `@afpia/prettier`, `@afpia/commitlint`.

Соблюдать направление зависимостей FSD:

```text
app -> pages -> widgets -> features -> entities -> shared
```

- `app` — запуск приложения и router; `pages` — композиция маршрута; `widgets` — крупные самостоятельные области.
- `features` — пользовательские действия; `entities` — предметные модели и пассивное отображение; `shared` — общая
  инфраструктура и UI primitives.
- Pinia stores хранить в `src/shared/stores`, router — в `src/app`, assets и глобальные стили — в `src/shared/assets`.
- Общий HTTP/TMDB-клиент хранить в `src/shared/api`, feature-specific запросы — в `api` соответствующей feature.
- Логику slice разделять на `model`, `api`, `lib`, `ui` по назначению. Не создавать пустые слои и папки ради структуры.
- Между slices импортировать только публичный `index.ts` через настроенные aliases; внутри модуля использовать
  относительные импорты.

## Код и интерфейс

- Не использовать `any`; внешние данные принимать как `unknown` и проверять на границе.
- Не скрывать ошибки типов необоснованными assertions. Предпочитать string unions и `as const` вместо `enum`.
- Публичные функции, props, emits и API-контракты типизировать явно; типы импортировать через `import type`.
- Использовать именованные экспорты, кроме обязательного default export фреймворка.
- Raw `fetch`, сериализация storage и тяжёлая бизнес-логика запрещены в компонентах.
- Локальное UI-состояние держать в компоненте или composable; глобальное — в Setup Store.
- Использовать существующие компоненты shadcn-vue, не писать дубликаты Select, Combobox, Button и других controls.
- Код и идентификаторы писать на английском, документацию и UI — на русском. Не оставлять `console.log`.

Порядок Vue SFC:

```vue
<script setup lang="ts"></script>

<template></template>

<style scoped src="./ComponentName.css"></style>
```

CSS компонента хранить рядом в файле с тем же PascalCase basename. Inline CSS и Tailwind за пределами `shared/ui` не
использовать. Интерфейс проектировать от 360 px, без горизонтального скролла, с клавиатурным управлением,
`focus-visible` и доступными именами controls.

## Тесты и команды

PR в `dev` и `main` проверяются GitHub Actions: `Validate` и `Build`; настройки описаны в `docs/ci`.
CI не использует секреты и не подключает платный AI API. Merge выполняет владелец вручную.

- Бизнес-логику покрывать Vitest, поведение компонентов — Vue Test Utils.
- Тесты хранить рядом в `__tests__/*.spec.ts`; проверять публичное поведение, ошибки и критические переходы.
- Внешние ответы TMDB валидировать и тестировать как неизвестные данные. Большие snapshot-тесты страниц не использовать.
- Для значимого требования обновлять тесты и трассировку в `spec.md`.

```sh
yarn dev
yarn test:unit
yarn test:unit:watch
yarn type-check
yarn lint
yarn format:check
yarn validate
yarn build
yarn commit
```

Для документации выполнить минимум `yarn format:check` и `yarn lint`. Для кода и tooling выполнить `yarn validate`, а
для значимой реализации также `yarn build`.

## Ограничения

- Не добавлять backend, realtime, авторизацию или стороннюю платформу без явного решения владельца.
- Не выдавать frontend-имитацию за настоящий мультиплеер.
- Не хранить секреты и TMDB token в отслеживаемых файлах.
- Не редактировать generated и lock-файлы вручную, если это должен делать инструмент.
- Не изменять посторонние файлы грязного worktree и не удалять используемое поведение ради упрощения задачи.
- Не применять разрушительные Git-команды, `--no-verify` и переписывание истории без прямого запроса.
- Не объявлять работу завершённой при падающих обязательных проверках; внешнюю блокировку описать явно.

## Рабочий процесс

1. Проверить `git status` и сохранить несвязанные изменения пользователя.
2. Определить тип изменения; выбрать ветку по разделу «Ветки и pull requests», прочитать код и существующие требования.
3. Для фичи или крупной задачи применить `sdd-feature`; для небольшого технического исправления составить короткий план
   при необходимости. Правки внутренних инструкций не требуют продуктовой спецификации сами по себе.
4. Реализовать минимальное связное изменение в правильном FSD-слое.
5. Применить `verify-changes`, просмотреть diff и исключить посторонние файлы.
6. После каждого законченного смыслового действия применить `commit-changes` и создать отдельный атомарный коммит.
7. Завершённую feature-ветку отправить на GitHub и открыть PR в `dev`; сообщить результат, проверки, ограничения и ссылку.

Если продолжение требует выбора новой технологии, внешней системы или расширения задачи, запросить решение владельца.

## Git

`main` и `dev` защищены: любые изменения отправлять из отдельной рабочей ветки через PR, включая небольшие исправления.
Прямой push в эти ветки не использовать. Обязательные проверки `Validate` и `Build` нельзя обходить.
Обязательное AI-одобрение не требуется. Слияние выполняет владелец вручную.

### Ветки и pull requests

- `main` — стабильная версия. Не вести в ней разработку и не отправлять туда рабочие коммиты напрямую.
- `dev` — основная ветка разработки и база новых задач; на GitHub используется как default branch.
- Фичи и крупные задачи выполнять в `feature/<short-kebab-case-name>`, созданной от актуальной `origin/dev`.
  Использовать написание `feature/`. Спецификации, план и задачи добавлять уже в этой ветке, до реализации.
- Перед началом выполнить fetch и проверить расхождение локальной `dev` с `origin/dev`. Чистую локальную `dev`
  обновлять через fast-forward; не сбрасывать пользовательские коммиты, не выполнять автоматический rebase или stash.
  Подходящую ветку текущей задачи переиспользовать; изменения другой задачи в неё не переносить.
- Небольшие технические исправления выполнять в `fix/<short-kebab-case-name>` через PR в `dev` без нового SDD-пакета.
  Размер задачи сам по себе не требует новых технологий или расширения объёма.
- Запрос на реализацию фичи включает создание ветки, атомарные коммиты, push этой ветки и создание PR с base `dev`.
  Перед открытием PR проверить весь diff относительно `origin/dev`, а не только последний коммит; не создавать дубли PR.
- PR описывает итоговое поведение, связанный SDD-пакет, выполненные проверки и ограничения. Незавершённую работу
  не выдавать за готовую: PR при необходимости открывать как draft с явным описанием оставшихся задач.
- После успешных проверок оставить PR открытым владельцу. Не нажимать Merge, не включать auto-merge и не удалять ветку
  до решения владельца. Решение о слиянии принимает владелец вручную.
- Выпуск `dev` → `main`, production-деплой, изменение branch protection и настройка бота требуют отдельного запроса владельца.
  Настройка Git-flow сама по себе не подключает автоматические деплои и не меняет настройки Vercel.
- Запросы только на анализ или ревью не разрешают создание веток, коммитов или PR.

### Сообщения коммитов

Коммит должен проходить `@afpia/commitlint`. Формат:

```text
<emoji> <type>(<scope>): <русский subject с отглагольным существительным в именительном падеже>
```

Примеры, совместимые с текущим `@afpia/commitlint`:

```text
✨ feat(game): добавление таймера раунда
🐛 fix(game): исправление подсчёта очков
🚀 refactor(tmdb): разделение API-клиента
```

Допустимые пары: `✨ feat`, `🐛 fix`, `📚 docs`, `💎 style`, `🚀 refactor`, `🚨 test`, `🛠️ build`, `♻️ chore`,
`🗑️ revert`, `🔥 init`. `type` и `scope` — технические латинские идентификаторы. Не смешивать несвязанные изменения и
не коммитить исследовательское или заведомо сломанное состояние. Добавлять в index только относящиеся к действию файлы.
Не выполнять amend, squash или rebase без прямого запроса владельца.
